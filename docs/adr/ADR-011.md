# ADR-011: Bounded replay projections with a browser playback cursor

- Status: Accepted
- Date: 2026-09-20

## Context

An interviewer should be able to follow telemetry through normalization, rule
matches, alerts and incident correlation. The public PostgreSQL fixture must stay
unchanged. The hosted API and Next.js proxy currently exchange bounded JSON;
long-lived streams would require changing their timeout and disconnect contracts.

## Decision

Compute a finite replay projection for a known scenario. The detector processes
ordered telemetry once. Its causal signals are released at their triggering event;
correlation receives only alerts and events available at that point. Frames expose
the actual normalization, match, alert and correlation results. An incident appears
only after the configured threshold, and its evidence grows as input arrives.

The original Atlas corpus retains all 4,026 events. Replay explicitly initializes
its 4,000 normal background events, verifies that they generated no alerts, then
plays the 26 investigation observations. Smaller scenarios play every event.
Displayed initialization and playback counts make this focus explicit.

A GET returns the bounded projection. The browser owns Start/Pause/Resume/Step/
Reset and playback speed; it does not submit visitor state to the API. The entire
projection is available to the client, so playback is a presentation of computed
history, not an access-control mechanism hiding future events. Each individual
frame nevertheless contains only state justified at its event-time prefix.

Serialized cache values are bounded to the finite corpus; callers receive fresh
objects. Resource limits cover event/frame/output counts as well as existing
public request and concurrency budgets. Timing logs contain counters and duration,
not telemetry, prompts or credentials. Required replay execution never calls AI.

The runtime contract advertises versioned capabilities additively. Existing mode,
read-only, provider and curated-question checks retain their meaning. A new
frontend must hide unavailable features when paired with an older backend during
a staggered deployment; capabilities describe availability, not authorization.

## Consequences

This is deterministic fixture replay, not live ingestion or a streaming security
platform. No broker, SSE, WebSocket, persistent replay-run table or per-visitor
registry is needed. Disconnecting or resetting cannot leave a server session or
change canonical evidence. UI timers can compress disclosed idle gaps for a
rehearsable demo; event timestamps and order remain authoritative.

SSE was considered but adds no value when the full bounded source is already
known. A future real ingestion requirement would need its own delivery, backpressure,
retention and authorization design rather than extending this playback contract.
